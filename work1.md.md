# Git rebase
## Заголовок 2 (Подтема)

**git rebase (перебазирование)** — это процесс переноса ветки коммитов на новую базовую основу (новый родительский коммит).

• Главная цель: Поддержание чистой, красивой, линейной истории без лишних «мерж-коммитов» (Merge branch...).
• Золотое правило: Никогда не делать rebase публичных веток (например, main или develop), если с ними одновременно работают другие инженеры. Это перезаписывает историю и ломает чужие репозитории.

## Синтаксис
**git rebase <из_какой_ветки_подтягиваем>**

*Применяется, когда вы сидите в своей фича-ветке и хотите «подтянуть» в неё последние изменения из main, перенеся свои коммиты на самый верх.*

## Конфликт
При возникновении конфликтов rebase останавливается. Управление процессом происходит с помощью следующих ключей:
• *--continue* — продолжить процесс rebase после того, как конфликты в текущем коммите успешно разрешены вручную и файлы добавлены через git add.
• *--abort* — полностью отменить операцию rebase. Ветка возвращается в абсолютно то же состояние, в котором она была до ввода команды.
• *--skip*— пропустить текущий коммит, вызвавший конфликт (изменения этого коммита будут полностью потеряны). Используется редко.
• *--quit*— немедленно выйти из процесса rebase. Текущие изменения на диске останутся, но Git больше не будет считать, что вы находитесь в режиме перебазирования (аналогично тому, как это работает в revert).


## Интерактивный режим: git rebase -i
*Позволяет «причесать» историю коммитов перед отправкой кода в общий репозиторий.*
 
**git rebase -i HEAD~[количество_коммитов]**
Пример: git rebase -i HEAD~5 (откроет последние 5 коммитов)

После запуска открывается текстовый редактор (обычно Vim), где напротив каждого коммита стоит ключевое слово. Заменив его, вы меняете судьбу коммита:


**pick (p)**	pick	Оставить коммит как есть (по умолчанию).
**reword (r)**	reword	Оставить коммит, но изменить только его текстовое сообщение.
**edit (e)**	edit	Остановить rebase на этом коммите для редактирования файлов или тестирования.
**squash (s)**	squash	Склеить коммит с предыдущим (вышестоящим), объединив их сообщения в одно.
**fixup (f)**	fixup	Склеить коммит с предыдущим, но выбросить (удалить) сообщение текущего коммита. Идеально для коммитов типа "fix typo".
**drop (d)**	drop	Полностью удалить коммит из истории вместе с его изменениями.



## Продвинутые ключи

**git rebase --onto <newbase> <upstream> <branch>**
git rebase --onto main B

*Позволяет вырезать кусок ветки и пересадить его на другую основу, игнорируя промежуточного родителя.*
Сценарий: Ветка feature: main → A → B → C → D → E
Хочешь: отбросить A и B, перенести C, D, E поверх актуального main.

git checkout feature
git rebase --onto main B

Читается так: «возьми коммиты, которые идут после B (то есть C, D, E), и положи их на main».
Третий аргумент (feature) можно не указывать, если ты уже на этой ветке.


**git rebase -X theirs/ours**
*Используется для автоматического прохождения конфликтов без участия человека.*

theirs — при любых конфликтах автоматически выбирать изменения из накатываемой ветки (той, которую переносим).

ours — автоматически сохранять код из базовой ветки (на которую накатываем).


git checkout feature  
**git rebase main -X ours**  
Вы говорите Git: «При любых конфликтах оставляй код из базовой ветки (main), на которую я накатываю свои изменения».

Использование git rebase main -X theirs  
Вы говорите Git: «При любых конфликтах бери изменения из моей ветки (feature), которую я сейчас переношу».



**git rebase --no-verify**
*Игнорирует запуск локальных Git-хуков (например, pre-rebase), настроенных в репозитории. Экономит время в CI-пайплайнах, если проверки кода уже выполняются на стороне сервера.*

**git rebase --keep-empty**
*По умолчанию, если в результате squash или изменения кода коммит становится «пустым» (не вносит никаких правок в файлы), Git его удаляет. Этот флаг заставляет Git сохранить пустой коммит в истории.*

**git rebase -i --autosquash**
*Автоматически сортирует и подготавливает коммиты к склейке, если вы заранее называли их как fixup! [сообщение] или squash! [сообщение]. Очень удобно для автоматизации локальной работы.*


##  Как отправлять rebase на удаленный сервер (Pushing)

Поскольку rebase изменяет хэши коммитов, локальная ветка начнет конфликтовать с удаленной на сервере (origin). Обычный git push не сработает.
• ❌ **git push --force (-f)** — Запрещено. Безусловно перезаписывает ветку на сервере. Если ваш коллега успел отправить свой коммит в эту же ветку, --force сотрет его код навсегда.
• ✅ **git push --force-with-lease** — Безопасный force. Git проверит, совпадает ли состояние ветки на сервере с вашей локальной копией origin/branch. Если кто-то успел залить новые коммиты, Git заблокирует операцию, предотвращая потерю данных.



**Различия Merge и Rebase**

Для конспекта полезно иметь краткое сравнение двух подходов:

**git merge** 	git rebase
История 	
**Нелинейная (сохраняет все ветвления как есть).**	
Идеально линейная (все коммиты идут друг за другом)

Мерж-коммиты	
**Создает специальный коммит слияния.**
Не создает новых мерж-коммитов

Изменение истории 
**Безопасно. Существующие коммиты не меняются**	
Модифицирует историю (создает новые хэши коммитов)

Разрешение конфликтов 
**Все конфликты решаются один раз в конце**
Конфликты могут решаться пошагово для каждого коммита.

!!!
Не делай rebase веток, которые уже кто-то забрал. Rebase — для своих локальных веток, которые ещё не разошлись по другим людям. Если ветка общая — используй merge, он не переписывает историю.

И если уж пришлось force-push'ить — предупреди коллегу, чтобы он сделал git fetch + git reset --hard origin/feature (а не обычный pull), и заранее сохранил свои коммиты.


В обычном git merge: ours — это ветка, в которую вы вливаете (куда вы переключились), а theirs — это ветка, которую вы вливаете. В git rebase всё наоборот.



# git merge

git merge (слияние) — это классический способ объединения изменений из одной ветки в другую. В отличие от rebase, merge не переписывает историю коммитов, а сохраняет её в исходном нелинейном виде, создавая (в большинстве случаев) специальный коммит слияния.

1. Два режима работы git merge

Когда вы запускаете слияние (например, находясь в main и выполняя git merge feature), Git может пойти по одному из двух путей в зависимости от состояния истории:

**Fast-Forward (Перемотка вперед)**
Происходит автоматически, если с момента создания ветки feature в целевой ветке main не появилось новых коммитов.
• Механика: Git не создает новый коммит слияния. Он просто перемещает указатель main вперед на самый последний коммит ветки feature.
• Результат: История остается идеально линейной.

**Three-Way Merge (Трехстороннее слияние)**

Происходит, если после разделения веток и в main, и в feature появились новые коммиты.
• Механика: Git находит общего предка обеих веток (Base), берет последние коммиты из обеих веток и объединяет их изменения.
• Результат: Автоматически создается коммит слияния (Merge commit), у которого будет сразу два родителя. История становится нелинейной (граф разветвляется и снова сходится).

2. Ключевые опции и флаги управления слиянием

Эффективное управление стратегией интеграции кода в CI/CD пайплайнах и командной работе строится на следующих ключах:


--no-ff (Запретить Fast-Forward)
**git merge --no-ff feature**

• Зачем нужен: Принудительно создает коммит слияния, даже если Git мог бы сделать обычную перемотку (Fast-Forward).
• Применение в DevOps: Это стандарт для GitFlow. Позволяет сохранить в истории явный факт того, что группа коммитов разрабатывалась в отдельной ветке. При удалении фича-ветки её контур и история интеграции останутся видны на графе.


--ff-only (Только Fast-Forward)
**git merge --ff-only feature**

• Зачем нужен: Разрешает слияние только в том случае, если история линейна и возможна простая «перемотка». Если в целевой ветке есть новые коммиты, Git выдаст ошибку и прервет операцию.
• Применение в DevOps: Идеально для автоматических скриптов в CI/CD при обновлении локальных веток с сервера (git pull --ff-only), чтобы случайно не наплодить локальных мерж-коммитов.


--squash (Сжатие коммитов при слиянии)
**git merge --squash feature**

• Зачем нужен: Берет все изменения из ветки feature, объединяет их в один плоский кусок кода и помещает в ваш рабочий каталог и индекс целевой ветки, не создавая коммит автоматически. Вам нужно вручную написать git commit.
• Результат: В ветку main попадает всего один аккуратный коммит со всеми изменениями, а история разработки фичи (со всеми промежуточными коммитами типа «fix typo») полностью скрывается. В отличие от rebase -i, исходная ветка feature никак не модифицируется.


--no-commit
**git merge --no-commit feature**

• Зачем нужен: Выполняет слияние и подготавливает коммит слияния, но останавливается прямо перед его фиксацией. Это дает инженеру возможность проверить результат работы, запустить тесты или вручную скорректировать файлы до того, как мерж запишется в историю.

3. Управление конфликтами при слиянии

Если одни и те же строки в файлах были изменены в обеих ветках, git merge остановится с ошибкой конфликта.

Флаги управления:

*git merge --continue* — продолжить процесс создания мерж-коммита после того, как вы вручную разрешили конфликты в файлах и зафиксировали их через git add.
*git merge --abort* — полностью отменить слияние и вернуть репозиторий в состояние «до ввода команды».
*git merge --quit* — прекратить операцию слияния, но оставить текущие измененные файлы на диске (индекс и состояние репозитория очищаются от флага "в процессе слияния")


Стратегии автоматического слияния (-X / --strategy-option):

Используются для автоматизации в CI/CD скриптах (авто-мерж при успешных билдах):
• git merge -X ours — при конфликтах автоматически брать версию файла из текущей ветки (в которой вы сидите, например, main).
• git merge -X theirs — при конфликтах автоматически брать версию из вливаемой ветки (которую вы мержите, например, feature).
• 📌 Важно: При merge понятия ours (наше) и theirs (их) абсолютно логичны и интуитивны, в отличие от rebase, где они меняются местами.
