# Git rebase

**git rebase (перебазирование)** — это процесс переноса ветки коммитов на новую базовую основу (новый родительский коммит).  

• Главная цель: Поддержание чистой, красивой, линейной истории без лишних «мерж-коммитов» (Merge branch...).  
• Золотое правило: Никогда не делать rebase публичных веток (например, main или develop), если с ними одновременно работают другие инженеры. Это перезаписывает историю и ломает чужие репозитории.  

## Синтаксис
**git rebase <из_какой_ветки_подтягиваем>**  

*Применяется, когда вы сидите в своей фича-ветке и хотите «подтянуть» в неё последние изменения из main, перенеся свои коммиты на самый верх.*  

## Конфликт
При возникновении конфликтов rebase останавливается. Управление процессом происходит с помощью следующих ключей:  
• *--continue* — продолжить процесс rebase после того, как конфликты в текущем коммите успешно разрешены вручную и файлы добавлены через git add.  
• *--abort* — полностью отменить операцию rebase. Ветка возвращается в абсолютно то же состояние, в котором она была до ввода команды.  
• *--skip*— пропустить текущий коммит, вызвавший конфликт (изменения этого коммита будут полностью потеряны). Используется редко.  
• *--quit*— немедленно выйти из процесса rebase. Текущие изменения на диске останутся, но Git больше не будет считать, что вы находитесь в режиме перебазирования (аналогично тому, как это работает в revert).


## Интерактивный режим: git rebase -i
*Позволяет «причесать» историю коммитов перед отправкой кода в общий репозиторий.*  
 
**git rebase -i HEAD~[количество_коммитов]**  
Пример: git rebase -i HEAD~5 (откроет последние 5 коммитов)  

После запуска открывается текстовый редактор (обычно Vim), где напротив каждого коммита стоит ключевое слово. Заменив его, вы меняете судьбу коммита:  


**pick (p)**	pick	Оставить коммит как есть (по умолчанию).  
**reword (r)**	reword	Оставить коммит, но изменить только его текстовое сообщение.  
**edit (e)**	edit	Остановить rebase на этом коммите для редактирования файлов или тестирования.  
**squash (s)**	squash	Склеить коммит с предыдущим (вышестоящим), объединив их сообщения в одно.  
**fixup (f)**	fixup	Склеить коммит с предыдущим, но выбросить (удалить) сообщение текущего коммита. Идеально для коммитов типа "fix typo".  
**drop (d)**	drop	Полностью удалить коммит из истории вместе с его изменениями.  



## Продвинутые ключи

**git rebase --onto <newbase> <upstream> <branch>**  
git rebase --onto main B  

*Позволяет вырезать кусок ветки и пересадить его на другую основу, игнорируя промежуточного родителя.*  
Сценарий: Ветка feature: main → A → B → C → D → E  
Хочешь: отбросить A и B, перенести C, D, E поверх актуального main.  

git checkout feature  
git rebase --onto main B  

Читается так: «возьми коммиты, которые идут после B (то есть C, D, E), и положи их на main».  
Третий аргумент (feature) можно не указывать, если ты уже на этой ветке.  


**git rebase -X theirs/ours**
*Используется для автоматического прохождения конфликтов без участия человека.*  

theirs — при любых конфликтах автоматически выбирать изменения из накатываемой ветки (той, которую переносим).  

ours — автоматически сохранять код из базовой ветки (на которую накатываем).  


git checkout feature  
**git rebase main -X ours**  
Вы говорите Git: «При любых конфликтах оставляй код из базовой ветки (main), на которую я накатываю свои изменения».  

Использование git rebase main -X theirs    
Вы говорите Git: «При любых конфликтах бери изменения из моей ветки (feature), которую я сейчас переношу».  



**git rebase --no-verify**
*Игнорирует запуск локальных Git-хуков (например, pre-rebase), настроенных в репозитории. Экономит время в CI-пайплайнах, если проверки кода уже выполняются на стороне сервера.*  

**git rebase --keep-empty**
*По умолчанию, если в результате squash или изменения кода коммит становится «пустым» (не вносит никаких правок в файлы), Git его удаляет. Этот флаг заставляет Git сохранить пустой коммит в истории.*  

**git rebase -i --autosquash**
*Автоматически сортирует и подготавливает коммиты к склейке, если вы заранее называли их как fixup! [сообщение] или squash! [сообщение]. Очень удобно для автоматизации локальной работы.*  


##  Как отправлять rebase на удаленный сервер (Pushing)

Поскольку rebase изменяет хэши коммитов, локальная ветка начнет конфликтовать с удаленной на сервере (origin). Обычный git push не сработает.  
• ❌ **git push --force (-f)** — Запрещено. Безусловно перезаписывает ветку на сервере. Если ваш коллега успел отправить свой коммит в эту же ветку, --force сотрет его код навсегда.  
• ✅ **git push --force-with-lease** — Безопасный force. Git проверит, совпадает ли состояние ветки на сервере с вашей локальной копией origin/branch. Если кто-то успел залить новые коммиты, Git заблокирует операцию, предотвращая потерю данных.  



**Различия Merge и Rebase**

Для конспекта полезно иметь краткое сравнение двух подходов:  

**git merge** 	git rebase  
История 	  
**Нелинейная (сохраняет все ветвления как есть).**	  
Идеально линейная (все коммиты идут друг за другом)  

Мерж-коммиты	  
**Создает специальный коммит слияния.**  
Не создает новых мерж-коммитов  

Изменение истории   
**Безопасно. Существующие коммиты не меняются**	  
Модифицирует историю (создает новые хэши коммитов)  

Разрешение конфликтов  
**Все конфликты решаются один раз в конце**  
Конфликты могут решаться пошагово для каждого коммита.  

!!!  
Не делай rebase веток, которые уже кто-то забрал. Rebase — для своих локальных веток, которые ещё не разошлись по другим людям. Если ветка общая — используй merge, он не переписывает историю.  

И если уж пришлось force-push'ить — предупреди коллегу, чтобы он сделал git fetch + git reset --hard origin/feature (а не обычный pull), и заранее сохранил свои коммиты.  


В обычном git merge: ours — это ветка, в которую вы вливаете (куда вы переключились), а theirs — это ветка, которую вы вливаете. В git rebase всё наоборот.  



# git merge

git merge (слияние) — это классический способ объединения изменений из одной ветки в другую. В отличие от rebase, merge не переписывает историю коммитов, а сохраняет её в исходном нелинейном виде, создавая (в большинстве случаев) специальный коммит слияния.  

## Два режима работы git merge  

Когда вы запускаете слияние (например, находясь в main и выполняя git merge feature), Git может пойти по одному из двух путей в зависимости от состояния истории:  

**Fast-Forward (Перемотка вперед)**  
Происходит автоматически, если с момента создания ветки feature в целевой ветке main не появилось новых коммитов.  
• Механика: Git не создает новый коммит слияния. Он просто перемещает указатель main вперед на самый последний коммит ветки feature.  
• Результат: История остается идеально линейной.  

**Three-Way Merge (Трехстороннее слияние)**  

Происходит, если после разделения веток и в main, и в feature появились новые коммиты.  
• Механика: Git находит общего предка обеих веток (Base), берет последние коммиты из обеих веток и объединяет их изменения.  
• Результат: Автоматически создается коммит слияния (Merge commit), у которого будет сразу два родителя. История становится нелинейной (граф разветвляется и снова сходится).  

## Ключевые опции и флаги управления слиянием  

Эффективное управление стратегией интеграции кода в CI/CD пайплайнах и командной работе строится на следующих ключах:  


--no-ff (Запретить Fast-Forward)  
**git merge --no-ff feature**  

• Зачем нужен: Принудительно создает коммит слияния, даже если Git мог бы сделать обычную перемотку (Fast-Forward).  
• Применение в DevOps: Это стандарт для GitFlow. Позволяет сохранить в истории явный факт того, что группа коммитов разрабатывалась в отдельной ветке. При удалении фича-ветки её контур и история интеграции останутся видны на графе.  


--ff-only (Только Fast-Forward)  
**git merge --ff-only feature**  

• Зачем нужен: Разрешает слияние только в том случае, если история линейна и возможна простая «перемотка». Если в целевой ветке есть новые коммиты, Git выдаст ошибку и прервет операцию.  
• Применение в DevOps: Идеально для автоматических скриптов в CI/CD при обновлении локальных веток с сервера (git pull --ff-only), чтобы случайно не наплодить локальных мерж-коммитов.  


--squash (Сжатие коммитов при слиянии)  
**git merge --squash feature**  

• Зачем нужен: Берет все изменения из ветки feature, объединяет их в один плоский кусок кода и помещает в ваш рабочий каталог и индекс целевой ветки, не создавая коммит автоматически. Вам нужно вручную написать git commit.  
• Результат: В ветку main попадает всего один аккуратный коммит со всеми изменениями, а история разработки фичи (со всеми промежуточными коммитами типа «fix typo») полностью скрывается. В отличие от rebase -i, исходная ветка feature никак не модифицируется.  


--no-commit  
**git merge --no-commit feature**  

• Зачем нужен: Выполняет слияние и подготавливает коммит слияния, но останавливается прямо перед его фиксацией. Это дает инженеру возможность проверить результат работы, запустить тесты или вручную скорректировать файлы до того, как мерж запишется в историю.  

## Управление конфликтами при слиянии  

Если одни и те же строки в файлах были изменены в обеих ветках, git merge остановится с ошибкой конфликта.  

Флаги управления:  

*git merge --continue* — продолжить процесс создания мерж-коммита после того, как вы вручную разрешили конфликты в файлах и зафиксировали их через git add.  
*git merge --abort* — полностью отменить слияние и вернуть репозиторий в состояние «до ввода команды».  
*git merge --quit* — прекратить операцию слияния, но оставить текущие измененные файлы на диске (индекс и состояние репозитория очищаются от флага "в процессе слияния")  


Стратегии автоматического слияния (-X / --strategy-option):  

Используются для автоматизации в CI/CD скриптах (авто-мерж при успешных билдах):  
**git merge -X ours** — при конфликтах автоматически брать версию файла из текущей ветки (в которой вы сидите, например, main).  
**git merge -X theirs** — при конфликтах автоматически брать версию из вливаемой ветки (которую вы мержите, например, feature).  
• 📌 Важно: При merge понятия ours (наше) и theirs (их) абсолютно логичны и интуитивны, в отличие от rebase, где они меняются местами.  



# git cherry-pick  

git cherry-pick (дословно «выковыривание вишенок») — это команда, которая позволяет взять один или несколько конкретных коммитов из любой ветки репозитория и скопировать их изменения в вашу текущую ветку.  
• Главная цель: Точечный перенос изменений без слияния (merge) или перебазирования (rebase) веток целиком.  
• Основное отличие от merge/rebase: Вы не объединяете ветки, вы копируете только изолированные куски кода (коммиты). При этом Git создает в текущей ветке абсолютно новые коммиты с новым хэшем, но с тем же содержимым и автором.  

## Наглядный пример: Как это работает  

Представьте, что вы ведете разработку в ветке main. Ваш коллега работает в ветке feature над новой крупной задачей и сделал там 3 коммита: A, B и C.
В коммите B он случайно наткнулся на критический баг в авторизации и исправил его. Сама фича целиком (feature) еще сырая и не готова к релизу, поэтому делать git merge нельзя. Но исправление бага вам нужно в ветке main прямо сейчас.  

## Полный синтаксис и варианты использования  

Вы можете забирать коммиты самыми разными способами:  
• git cherry-pick <commit_hash> — скопировать один конкретный коммит.  
• git cherry-pick <hash1> <hash2> <hash3> — скопировать несколько отдельных коммитов за раз (применятся по очереди).  
• git cherry-pick <hashA>..<hashB> — скопировать диапазон коммитов от hashA до hashB (включительно). Важно: изменения самого hashA в этот диапазон не входят, они служат точкой отсчета.  


## Ключевые опции и флаги  

• *-n / --no-commit* — один из главных флагов для автоматизации и проверок. Git применяет изменения из коммита к файлам и добавляет их в индекс (Staging Area), но не создает коммит автоматически.  
	Зачем: Позволяет запустить локальные тесты на скопированном коде, отредактировать файлы или объединить сразу несколько разных «черри-пиков» в один единственный аккуратный коммит.  
• *-x*— автоматически добавляет в конец сообщения коммита системную строчку вида: (cherry picked from commit 4f9d2e8...).  
	Зачем: Это стандарт хорошего тона в разработке. Помогает команде и CI/CD скриптам отслеживать происхождение кода и понимать, откуда этот коммит был скопирован.  
• *-e / --edit* — перед фиксацией коммита открывает текстовый редактор (например, Vim), чтобы вы могли изменить стандартное сообщение коммита.  
• *-s / --signoff* — добавляет строчку Signed-off-by: в конец сообщения коммита (подтверждение авторства/проверки, часто требуется в корпоративных политиках и open-source).  
• *-m <parent-number> / --mainline* — необходим для «черри-пика» коммитов-слияний (merge commits). Поскольку у мерж-коммита всегда два и более родителя, Git не знает, изменения какой именно ветки считать «своими», а какие накатывать. Флаг указывает номер родителя (обычно 1 — это ветка, в которую когда-то шло слияние).  
  Пример: git cherry-pick -m 1 <merge_commit_hash>  


## Автоматическое разрешение конфликтов в скриптах (-X):  

Если cherry-pick выполняется внутри пайплайна (CI/CD) и человека рядом нет, можно задать стратегию поведения:  
• *git cherry-pick -X ours <hash>* — при любых конфликтах автоматически отдавать приоритет коду из вашей текущей ветки.  
• *git cherry-pick -X theirs <hash>* — при конфликтах затирать старый код изменениями из копируемого коммита.  


## Пример 1: Экстренное исправление на продакшене (Hotfix)  

Сценарий: На продакшене (ветка production) обнаружена критическая уязвимость. Разработчик Вася быстро создал ветку bugfix-auth, исправил её в коммите c3a5e12 и отправил тестировщикам в ветку testing.  
Менеджер говорит: "Тестирование всей ветки займет два дня, но этот баг нужно закрыть на проде прямо сейчас!". Вам нужно перенести только этот один коммит в production.  

Пошаговое выполнение:  

1. Переключаемся на ветку продакшена  
**git checkout production**  

2. Подтягиваем последние изменения с сервера, чтобы ветка была актуальной  
**git pull origin production**  

3. Применяем cherry-pick с флагом -x, чтобы в истории остался след, откуда взят этот коммит  
**git cherry-pick -x c3a5e12**  

4. Git успешно применяет изменения и автоматически создает новый коммит. Проверяем историю с помощью git log -n 1  
*commit a4b2c8d (HEAD -> production)*  
*Author: Vasya <vasya@company.com>*  
*Date:   Sat Nov 7 12:00:00 2026 +0300*  
  
*Fix SQL injection in login form*  

*(cherry picked from commit c3a5e128913b7f64d08126e7b)*  

5. Отправляем готовый фикс на сервер для автоматического деплоя  
**git push origin production**  



## Пример 2: Сборка релиза из разных веток с помощью cherry-pick -n (без автокоммита)  

Сценарий: Вы готовите аналитический отчет или скрипт автоматизации деплоя для нового сервера (ветка deploy-prod). У вас есть три разных разработчика, каждый из которых написал по одной полезной функции в своих изолированных ветках. Их коммиты: 1a1a1a1 (скрипт бэкапа), 2b2b2b2 (настройка логирования) и 3c3c3c3 (конфиг мониторинга).
Вы хотите забрать все три изменения, но не хотите плодить три отдельных коммита в вашей ветке. Вам нужен один красивый коммит «Настройка окружения сервера».  

Пошаговое выполнение:  

1. Переходим в целевую ветку деплоя  
**git checkout deploy-prod**  
  
2. Забираем все три коммита за раз, используя ключ -n (или --no-commit)  
**git cherry-pick -n 1a1a1a1 2b2b2b2 3c3c3c3**  
  
3. Проверяем, что произошло, через git status  
*On branch deploy-prod*  
*Changes to be committed:*  
  *(use "git restore --staged <file>..." to unstage)*  
    *new file:   backup.sh*  
    *modified:   logger.conf*  
    *new file:   metrics.yaml*  
  
Все три изменения применились к файлам и закинуты в индекс (Staging Area), но коммита в истории еще нет.  

4. Теперь вы можете протестировать эти скрипты вместе. Если всё работает, делаем один аккуратный коммит вручную  
**git commit -m "Ops: Интеграция скриптов бэкапа, логирования и мониторинга для продакшена"**  



## Пример 3: Разрешение конфликтов при cherry-pick  

Сценарий: Вы пытаетесь скопировать коммит 8e9f1a2 из ветки feature в ветку main. Но в коммите изменялся файл config.yaml, который в ветке main уже успели сильно переписать.    
  
Пошаговое выполнение:  
  
1. Запускаем команду  
**git cherry-pick 8e9f1a2**  
  
2. Git выдает ошибку конфликта  
*error: could not apply 8e9f1a2... Update database timeout*
*hint: after resolving the conflicts, mark the corrected paths*
*hint: with 'git add <paths>' or 'git rm <paths>'*
*hint: and run 'git cherry-pick --continue'*

3. Открываем git status, чтобы увидеть проблемный файл  
**config.yaml**  
  
4. Открываем config.yaml в редакторе (например, в Vim) и видим маркеры конфликта  
database:  
<<<<<<< HEAD  
  host: prod-db.local  
  timeout: 30  
=======  
  host: test-db.local  
  timeout: 60  
СТРЕЛКА>>>>> 8e9f1a2... Update database timeout  

5. Разрешаем конфликт руками: Нам нужен хост от продакшена (prod-db.local), но таймаут мы хотим поставить новый (60). Удаляем маркеры Git и приводим файл к такому виду:  
*database:*  
  *host: prod-db.local*  
  *timeout: 60*  
  
6. Сохраняем файл и добавляем его в индекс  
**git add config.yaml**  
  
7. Завершаем операцию cherry-pick  
**git cherry-pick --continue**  
  
Git откроет текстовый редактор, предложит стандартное сообщение коммита, вы сохраняете его, и процесс успешно завершается.  
  
  
  
# Git Reflog  
  
git reflog (Reference Log — журнал ссылок) — это локальная «черная коробка» репозитория. Git записывает туда абсолютно любое изменение указателей веток и указателя HEAD на вашем компьютере.  
⚡️ Главное правило DevOps: Если изменения были хотя бы один раз закоммичены или сохранены в stash, они не исчезают бесследно. Даже если вы стерли ветку, сделали reset --hard или полностью сломали историю через rebase, git reflog поможет восстановить код.  
📂 Где хранится: Только локально на вашей машине в папке .git/logs/. Журнал reflog никогда не отправляется на сервер при git push. По умолчанию Git хранит эти записи от 30 до 90 дней.  

## 🛠 1. Анатомия вывода git reflog

Запустив команду git reflog, вы увидите список событий в хронологическом порядке (самые свежие действия всегда находятся сверху):  
  
*a1b2c3d HEAD@{0}: reset: moving to HEAD~1*  
*4e5f6g7 HEAD@{1}: commit: Fix auth bug*  
*7h8i9j0 HEAD@{2}: checkout: moving from feature to main*  
  
• a1b2c3d — хэш коммита (указателя), на который сместился HEAD в результате этого действия.  
• HEAD@{0} — индекс записи (индикатор времени). HEAD@{0} — текущее положение, HEAD@{1} — предыдущий шаг, и так далее.  
• reset: moving... / commit:... — описание операции, которая привела к изменению (переключение веток, коммит, сброс, слияние).  
  
## 🚨 2. Практические сценарии спасения кода  
  
  
Сценарий А: Отмена ошибочного git reset --hard  
  
Ситуация: Вы написали отличный код и сделали коммит «Feature: Добавлен бэкап». Затем решили поэкспериментировать, но запутались и жестко откатились командой git reset --hard HEAD~1.  
Через секунду вы понимаете: «О нет! Я сбросил не тот коммит! Весь мой утренний код стерт с диска!». Обычный git log этот коммит больше не показывает.  
Решение:  
1. Открываем журнал перемещений HEAD  
**git reflog**  
  
2. Ищем строчку, которая была прямо до сброса (до операции reset)  
*7a8b9c0 HEAD@{0}: reset: moving to HEAD~1*  
*4f5e6d7 HEAD@{1}: commit: Feature: Добавлен бэкап*  <-- ВОТ ОН, ЖИВОЙ!  
*1a2b3c4 HEAD@{2}: checkout: moving from dev to main*  

3. Возвращаем код одним из способов:  
	• Способ 1 (Жесткий): Вернуть текущую ветку обратно на этот коммит (внимание: сотрет текущие незакоммиченные файлы на диске)
**git reset --hard 4f5e6d7**  
  
	• Способ 2 (Безопасный): Создать от этого "потерянного" коммита новую временную ветку для проверки файлов  
**git branch recovery-branch 4f5e6d7**  
  
  
Сценарий Б: Спасение ветки после неудачного git rebase  
  
Ситуация: Вы делали интерактивный ребейз (git rebase -i main), чтобы склеить коммиты в своей ветке feature. Во время разрешения конфликтов вы случайно выбрали команду drop вместо pick для важного коммита, завершили rebase, и код просто испарился из истории.  
Решение:  
1. Запускаем  
**git reflog**

2. Внимательно читаем историю операций снизу вверх. Ищем строчку, где rebase только начинался (момент checkout main перед стартом или операция rebase (start))  
*b5v4c3x HEAD@{0}: rebase (finish): returning to refs/heads/feature*  
... (тут идут пошаговые накаты коммитов) ...  
*9f8e7d6 HEAD@{5}: rebase (start): checkout main*  
*3c2b1a0 HEAD@{6}: commit: Важный коммит, который я потерял*  <-- Состояние ДО ребейза  


3. Сбрасываем ветку к идеальному состоянию до начала ребейза  
**git reset --hard 3c2b1a0**  
  
Сценарий В: Восстановление случайно удаленной ветки целиком  
  
Ситуация: Вы работали в локальной ветке old-feature. Решив, что она больше не нужна, вы перешли в main и удалили её через git branch -D old-feature. Через час выясняется, что код из этой ветки критически нужен для релиза. Самой ветки больше нет ни локально, ни на сервере.  
Решение:  
1. Открываем reflog  
**git reflog**  

2. Ищем последнее действие, которое вы совершали, находясь внутри удаленной ветки (например, последний коммит в ней или момент переключения с неё)  
*1a2b3c4 HEAD@{0}: checkout: moving from main to dev*  
*5e6f7g8 HEAD@{1}: checkout: moving from old-feature to main* <-- Точка ухода из ветки  
*999z888 HEAD@{2}: commit: Окончательная настройка конфигов*     <-- Последний коммит в ветке  
  
3. Восстанавливаем ветку одной командой, просто создав её заново от найденного хэша  
**git branch old-feature 999z888**  
  
  
  
## ⚡️ 3. Продвинутые фишки и лайфхаки  
   
• Reflog конкретной ветки: По умолчанию команда показывает историю HEAD (все ваши перемещения по репозиторию). Чтобы сузить поиск и посмотреть историю изменений только конкретной ветки, используйте  
**git reflog show main**
  
• Привязка к календарному времени: Вместо индексов вроде HEAD@{1} можно использовать понятные временные интервалы (Git сам высчитает, где находился указатель в указанный момент)  
**git reset --hard HEAD@{yesterday}**      # Вернуть состояние, бывшее вчера  
**git reset --hard HEAD@{"2 days ago"}**   # Вернуть состояние 2 дня назад  
**git reset --hard HEAD@{"1:30 PM"}**     # Состояние на полвторого дня  
  
💡 Резюме для DevOps-инженера: Пока файлы были хотя бы один раз закоммичены, они живы. Если git log больше не видит ваш код — открывайте git reflog.    
  


# Папка .git  
  
Папка .git — это скрытая база данных репозитория, которая хранит всю историю изменений, ветки, настройки и черновики будущих коммитов. Без неё проект превращается в обычный набор файлов на диске.  
  
  
## 1. Главные указатели (Где мы сейчас находимся)  
  
• **HEAD**. Текстовый файл, который показывает, на какую ветку вы сейчас смотрите (обычно внутри написано ref: refs/heads/main). Если вы переключились на конкретный коммит без ветки (состояние detached HEAD), там будет записан 40-значный хэш этого коммита.  
• **ORIG_HEAD**. Страховочный файл. Перед опасными операциями (reset, rebase, merge) Git записывает сюда старый хэш коммита, чтобы вы могли быстро отменить изменения командой git reset --hard ORIG_HEAD.  
• **FETCH_HEAD**. Временный файл, куда записываются хэши веток, скачанных с сервера при последней команде git fetch или git pull.  
• **COMMIT_EDITMSG**. Временный файл, в котором сохраняется текст последнего введенного вами сообщения коммита.  
    
   
## 2. База данных и черновики (Как хранится код)  
  
• **objects/**. Главная база данных Git. Здесь хранятся все данные в сжатом виде, распределенные по папкам (первые 2 символа хэша SHA-1 — имя папки, остальные 38 — имя файла). Внутри лежат 4 типа объектов:  
  • *blob*. Чистое содержимое файла (не знает ни имени файла, ни прав доступа).  
  • *tree*. Аналог папки. Связывает имена файлов с их blob-объектами и другими подпапками.  
  • *commit*. Снимок состояния. Хранит ссылку на корневое tree, хэш родительского коммита, автора, дату и текст сообщения.  
  • *tag*. Аннотированный тег с именем автора, датой и описанием релиза.  
  
• **index**. Бинарный файл, который представляет собой Staging Area (индекс). Когда вы делаете git add, Git создает blob в objects/ и записывает связку «имя файла + хэш» в index, готовя будущий коммит.  
  
  
## 3. Ветки и история перемещений (Навигация)  
  
• **refs/**. Папка с обычными текстовыми файлами-ярлыками, внутри которых лежит всего одна строчка — хэш коммита:  
  • *refs/heads/*. Локальные ветки (например, файл main).  
  • *refs/remotes/*. Слепки удаленных веток с сервера (например, origin/main).  
  • *refs/tags/*. Указатели на фиксированные версии (теги).  
  
• **logs/**. Журнал всех перемещений указателей, который лежит в основе команды git reflog. Файл *logs/HEAD* помнит каждое переключение веток, reset, rebase и cherry-pick. Именно он позволяет спасти «удаленные» коммиты, пока их не удалил сборщик мусора (git gc).  
  
    
## 4. Настройки, автоматизация и наследие  
  
• **config**. Локальный файл настроек этого репозитория (адрес удаленного сервера origin, настройки веток, локальные имя и почта автора).  
• **info/**. Папка для вспомогательной информации. Чаще всего используется файл *info/exclude* — это локальный аналог *.gitignore*, который работает только на вашем компьютере и не попадает в общий репозиторий.  
• **hooks/**. Папка со скриптами (по умолчанию лежат примеры .sample). Позволяет запускать автоматические проверки (например, проверку стиля кода перед коммитом через скрипт pre-commit).  
• **branches/**. Пустая устаревшая папка из самых ранних версий Git. Создается автоматически для обратной совместимости со старыми скриптами и больше не используется.  
• **description**. Описание проекта для устаревшего веб-интерфейса GitWeb.  
  
Как это работает вместе: жизненный цикл коммита  
   
1. Вы делаете git add file.txt. Git сжимает текст файла, кладет его как blob в *objects/* и обновляет файл *index*.  
2. Вы делаете git commit. Git берет структуру из *index*, создает объект *tree*, затем создает объект *commit* в *objects/*.  
3. Обновление ссылок. Git смотрит в файл *HEAD*, находит активную ветку (например, refs/heads/main) и перезаписывает в неё новый хэш коммита.  
4. Запись в журнал. Старый и новый хэши записываются в *logs/HEAD* (чтобы сработал reflog).  
  
Команды для работы с «внутренностями» Git  
  
Если захочется посмотреть на всё это вживую без ручного поиска по папкам, используйте встроенные низкоуровневые команды (plumbing commands):  
  
**git cat-file -t <хэш>**	Показывает тип объекта в папке objects/ (commit, tree или blob).  
**git cat-file -p <хэш>**	Красиво выводит внутреннее содержимое любого объекта (текст файла, список файлов в tree или метаданные коммита).  
**git ls-files --stage**	Показывает содержимое бинарного файла index в читаемом текстовом виде.  
**git symbolic-ref HEAD**	Показывает, на какую ветку сейчас ссылается HEAD.  


Временные папки и файлы внутри .git — это служебные маркеры, которые Git создает для отслеживания прогресса многошаговых или прерванных операций. Они позволяют системе запомнить текущее состояние, чтобы вы могли безопасно продолжить процесс (--continue) или отменить его (--abort).  
  
1. Временные директории  
  
• **.git/rebase-merge/** и **.git/rebase-apply/**. Создаются во время перебазирования (git rebase и git rebase -i). Внутри хранятся план действий (git-rebase-todo), выполненные шаги (done), исходная ветка (head-name) и текст коммита (message).  
• **.git/sequencer/**. Появляется при переносе или отмене сразу нескольких коммитов (git cherry-pick или git revert с диапазоном). Содержит файлы todo и head для контроля очереди.  
• **.git/refs/bisect/**. Временная папка внутри директории ссылок, которая создается при бинарном поиске ошибок (git bisect). В ней лежат метки проверенных «хороших» (good) и «плохих» (bad) коммитов.  
  
2. Временные файлы-состояния (в корне .git/)  
  
• **MERGE_HEAD**, **MERGE_MSG**, **MERGE_MODE**. Возникают при конфликте во время слияния веток (git merge). Они фиксируют хэш вливаемого коммита и черновик сообщения для финального коммита.  
• **CHERRY_PICK_HEAD** и **REVERT_HEAD**. Создаются при остановке из-за конфликта во время одиночного git cherry-pick или git revert. Хранят ссылку на проблемный коммит.  
• **BISECT_START**, **BISECT_LOG**, **BISECT_NAMES**. Сопровождают процесс git bisect и запоминают исходную ветку, а также весь журнал проверок.  
• **AUTO_MERGE**. Служебный указатель, который сохраняет промежуточный результат автоматического объединения файлов при сложных конфликтах.  
• Файлы блокировки (**/*.lock/**). Временные файлы вроде index.lock или HEAD.lock, которые появляются на доли секунды при любой записи. Они защищают репозиторий от повреждения при одновременном запуске двух команд Git.  
  
  
3. Сводная шпаргалка по операциям  
  
Операция в Git________Временные папки и файлы____________________________________________Как удаляются  
git rebase / -i_______Папка **.git/rebase-merge/** или **.git/rebase-apply/**----------- git rebase --continue или --abort  
git merge_____________Файлы **MERGE_HEAD**, **MERGE_MSG**, **MERGE_MODE**--------------- git commit или git merge --abort  
git cherry-pick_______Файл **CHERRY_PICK_HEAD** или папка **.git/sequencer/**----------- git cherry-pick --continue или --abort  
git revert____________Файл **REVERT_HEAD** или папка **.git/sequencer/**---------------- git revert --continue или --abort  
git bisect____________Папка **.git/refs/bisect/** и файлы **BISECT_***------------------ git bisect reset  
  
Любая запись__________Файлы **index.lock**, **HEAD.lock**-------------------------------- Удаляются автоматически после завершения команды  




# Хуки, git gc и .gitignore    
  
Мы разберем, как автоматизировать рутину (Хуки), как оптимизировать базу данных, когда она начинает тормозить (git gc), и как скрыть от Git файлы, которым в истории не место (.gitignore).  
  
## Часть 1. Git Hooks (Хуки / Крючки) — Автоматизация процессов  
  
Представьте, что перед каждым коммитом вам нужно проверять код на ошибки (запускать линтер), а перед каждым git push — прогонять тесты. Делать это вручную лень, человек обязательно забудет. Для этого существуют хуки (hooks).  
💡 Git Hooks — это скрипты (сценарии), которые Git автоматически запускает при наступлении определенных ключевых событий (коммит, пуш, слияние веток и т.д.).  
  
Где они живут?  
  
Они находятся в скрытой папке репозитория: *.git/hooks/*.  
Если вы заглянете туда прямо сейчас, то увидите файлы с расширением .sample (например, pre-commit.sample, pre-push.sample). Это шаблоны на языке Bash. Чтобы хук заработал, достаточно удалить расширение .sample и написать туда свой код на любом языке программирования (Bash, Python, Node.js).  
  
Главные типы хуков:  
  
Хуки делятся на две группы: Client-side (работают на вашем компьютере) и Server-side (работают на сервере, например, в GitHub/GitLab).  
• pre-commit (на клиенте): Запускается до того, как вы введете сообщение коммита. Идеально подходит для автопроверки кода (форматирование, поиск забытых паролей). Если скрипт вернет ошибку, Git отменит коммит.  
• commit-msg (на клиенте): Проверяет текст вашего сообщения. Например, можно настроить так, чтобы Git не разрешал делать коммиты без указания номера задачи из Jira (например, TASK-123: fixed bug).  
• pre-push (на клиенте): Срабатывает перед отправкой кода на сервер. Здесь обычно запускают интеграционные тесты, чтобы не сломать сборку коллегам.  
• pre-receive (на сервере): Срабатывает на сервере, когда кто-то пушит код. Может полностью отклонить пуш, если код не соответствует правилам компании.  

Важно: Папка .git не отправляется на сервер, поэтому локальные хуки индивидуальны для каждого разработчика. Чтобы делиться ими с командой, используют сторонние инструменты (например, Husky для JavaScript проектов).  
  
  
## Часть 2. git gc (Garbage Collector) — Сборщик мусора и оптимизация  
  
В предыдущих практиках мы делали git reset --hard и перезаписывали историю через rebase. Вы видели, что «старые» коммиты исчезают из git log, но остаются в reflog и физически лежат в папке *.git/objects/*.  
Со временем таких «осиротевших» (dangling) коммитов, старых версий файлов и временных объектов становится слишком много. Папка .git разрастается, а Git начинает работать медленнее. Тут на сцену выходит git gc.  
💡 git gc (Garbage Collection) — это команда для очистки репозитория от мусора и оптимизации (сжатия) локальной базы данных.  
  
Что конкретно делает git gc?  

1. Удаляет мусор: Находит все объекты (blob, tree, commit), на которые больше не ссылается ни одна ветка, ни один тег и у которых истек срок хранения в reflog (по умолчанию старые «брошенные» объекты хранятся около 14–90 дней на случай, если вы захотите их спасти).  
2. Упаковывает файлы (Packfiles): Изначально каждый объект в .git/objects/ лежит как отдельный маленький файл. Если у вас тысячи файлов, операционная система начинает тратить много сил на их чтение. Git берет кучу мелких файлов, сжимает их по алгоритму дельта-компрессии (сохраняет только различия между версиями) и упаковывает в один большой бинарный .pack-файл, а старые удаляет.  
Обычно Git запускает git gc автоматически в фоновом режиме, когда накапливается слишком много свободных объектов. Можно сделать вручную - **git gc --prune=now**, если только что случайно закоммитили тяжелый фильм и хотите немедленно стереть его следы из базы.  
  
  
## Часть 3  .gitignore — Защита от лишних файлов  
  
Когда вы пишете код, в вашей рабочей папке неизбежно появляется «мусор»: папки виртуального окружения (.venv), кэш Python (__pycache__), системные файлы (.DS_Store или Thumbs.db), логи ошибок (error.log) или файлы конфигурации с секретными паролями от базы данных.  
Если вы случайно сделаете git add ., весь этот хлам улетит в репозиторий. Чтобы этого избежать, используется специальный файл.  
💡 .gitignore — это обычный текстовый файл в корне проекта, в котором перечисляются шаблоны имен файлов и папок, которые Git должен полностью игнорировать.  
В отличие от папки .git, файл .gitignore коммитится и отправляется на сервер, чтобы у всех разработчиков проекта были одинаковые правила фильтрации.  
  
Правила синтаксиса .gitignore:  
  
• # — Строки, начинающиеся с решетки, считаются комментариями.  
• error.log — Игнорировать конкретный файл с таким именем в любой папке.  
• node_modules/ — Слэш в конце означает, что нужно игнорировать всю папку со всем её содержимым.  
• *.log — Звёздочка означает «любое количество символов». Git проигнорирует app.log, server.log, 123.log.  
• !important.log — Восклицательный знак означает инверсию. Запретить игнорировать этот файл, даже если он подпадает под правило *.log.  
  
Золотое правило: Файл .gitignore работает только для тех файлов, которые еще не были добавлены в индекс. Если файл уже отслеживается Git (уже был закоммичен ранее), добавление его в .gitignore не поможет — сначала его нужно удалить из индекса командой git rm --cached <файл> (git rm -r --cached папка/).  
  
Создаем и настраиваем .gitignore  
Теперь создадим фильтр, который закроет этим файлам доступ в репозиторий. Откройте новый файл в редакторе:  
  
**vim .gitignore**  
  
Вставьте в него следующие правила (каждое с новой строки):  
  
• *.log  
• __pycache__/  
  
*Первая строка заблокирует любые лог-файлы, а вторая — всю папку кэша со всем её содержимым.*  
  
  
🧭 Итоговая шпаргалка  
  
• Хуки (.git/hooks/) — настраивают автоматические действия робота-помощника: проверяют код перед коммитом или пушем.  
• git gc — делает генеральную уборку в скрытой базе данных, сжимает историю и экономит место на диске.  
• .gitignore — работает как фейсконтроль на входе в репозиторий, не пуская системный мусор и секретные пароли в историю коммитов.  
  
  
  
**git checkout --orphan**         создать новую ветку без истории  
**git checkout -b (switch -c)**   создать новую ветку и переключиться на нее
    
**git rm -rf .**                 очищаем все файлы из директории и индекс от старых файлов (Неотслеживаемые файлы останутся)  
**git rm --cached <файл>**       удаляет файл только из области отслеживания(индекса)  
**git rm -r --cached папка/**    удалить папку из индекса  
  
  
  
  
# Git Stash  
  git stash — это команда, которая позволяет временно отложить незакоммиченные изменения, чтобы вернуть рабочую директорию в чистое состояние, а позже восстановить отложенное . Это нужно в ситуациях, когда ты работаешь над задачей, но срочно требуется переключиться на другую ветку, а коммитить «полуготовый» код не хочется.    
  
Типичный сценарий: ты правишь файлы, уже что-то добавил в индекс (git add), и тут приходит срочная задача. Вместо того чтобы делать WIP-коммит, ты выполняешь git stash, рабочая директория становится чистой, ты переключаешься и работаешь, а потом возвращаешь свои изменения обратно .  
  
  
Спрятать изменения  
  
**git stash**  
(или полный синоним)  
**git stash push**  
После выполнения команда выведет что-то вроде:  
*Saved working directory and index state WIP on master: 049d078 Create index file*  
*HEAD is now at 049d078 Create index file*  
  
Рабочая директория теперь чистая, а изменения лежат в специальном стеке.  
Можно добавить осмысленное сообщение:  
  
**git stash push -m "WIP: форма логина, недоделана валидация"**  
  
**git stash list** - посмотреть список отложенного  
  
Вывод:  
*stash@{0}: On master: WIP: форма логина, недоделана валидация*  
*stash@{1}: WIP on master: c264051 Revert "Add file_size"*  
*stash@{2}: WIP on master: 21d80a5 Add number to log*  
*stash@{0} — самый свежий, stash@{1} — предыдущий и так далее*  
  
Применить обратно  
  
Применить последний stash, оставив его в списке  
**git stash apply**  
  
Применить конкретный  
**git stash apply stash@{2}**  
  
Применить и сразу удалить из списка  
**git stash pop**  
  
Разница между apply и pop: apply только восстанавливает изменения, но оставляет запись в стеке; pop восстанавливает и удаляет запись  
  
Удалить конкретную запись  
**git stash drop stash@{0}**  
  
Удалить все   
**git stash clear**  
Команда необратима — записи становятся недоступны (хотя технически могут оставаться в reflog до prune).  
  
Посмотреть содержимое stash:  
Краткая статистика (какие файлы изменены)  
**git stash show**  
  
Полный diff  
**git stash show -p stash@{1}**  
По умолчанию show показывает diffstat, но с -p — полноценный патч .  
  
Полезные опции (то, что чаще всего нужно на практике)  
**--include-untracked / -u** — захватить неотслеживаемые файлы  
По умолчанию git stash прячет только отслеживаемые файлы. Если в проекте появились новые файлы (ещё не добавленные в Git), они останутся в рабочей директории. Чтобы захватить и их:  
  
**git stash push -u**  
**--all / -a** -  захватывает ещё и игнорируемые файлы (.gitignore)  
  
**--keep-index / -k** — оставить индекс нетронутым  
Ситуация: ты сделал git add для части изменений и хочешь закоммитить только их, а остальное отложить. --keep-index прячет изменения, но оставляет проиндексированное в индексе:  
**git stash push --keep-index**  
После этого можно сделать коммит только staged-части, а остальное останется в stash  
  
**--patch / -p** — интерактивно выбрать куски  
Позволяет спрятать не всё, а только выбранные ханки (фрагменты diff) в интерактивном режиме — как git add -p, но наоборот:  
**git stash push -p**  
Полезно, когда в одном файле смешаны изменения для двух разных задач  
  
  
**--index** при apply / pop — восстановить и индекс  
Обычный apply восстанавливает изменения в рабочей директории, но не возвращает их в индекс. Если при stash ты что-то добавлял через git add, после apply эти файлы окажутся unstaged. Чтобы восстановить и состояние индекса:  
**git stash apply --index**  
Это вернёт ровно то состояние, которое было до stash  
  
Продвинутый приём: git stash branch  
Если ветка, в которой ты сделал stash, ушла далеко вперёд, и git stash apply даёт конфликты, есть элегантное решение:  
  
**git stash branch new-branch-name stash@{0}**  
Git создаст новую ветку от того коммита, на котором был сделан stash, применит изменения без конфликтов (потому что база совпадает), и если всё пройдёт успешно — удалит запись из stash. Это удобнее, чем разрешать конфликты вручную.  
  
Что важно помнить  
Stash — это локальный стек. Он не пушится в удалённый репозиторий и не шарится с коллегами.  
apply не удаляет запись — не забывай делать drop или используй pop, иначе стек будет расти.  
clear необратим — если случайно очистил, запись может ещё какое-то время жить в reflog, но это не гарантия.  
Stash не заменяет коммит. Если работа большая и важная — лучше сделать WIP-коммит в отдельной ветке, чем держать всё в stash, который легко потерять.  
  
   
  
# Git Subtree и Submodule   
Обе технологии позволяют встроить один Git-репозиторий в другой, но делают это принципиально по-разному. Submodule хранит ссылку на внешний коммит, а subtree полностью вливает код и историю в основной проект.   
  
## Часть 1: Git Submodule  
  
Submodule — это указатель на конкретный коммит другого репозитория. В основном проекте хранится файл .gitmodules с метаданными, а сам код подмодуля лежит в отдельной папке и имеет собственную историю.  
  
Добавление  
  
git submodule add https://github.com/user/library.git vendor/library  
git commit -m "Add library as submodule"  
После этого создаётся .gitmodules, а в индексе фиксируется SHA коммита подмодуля.  
  
Клонирование проекта с submodule  
Обычный git clone не скачает содержимое подмодулей. Нужно либо:  
  
  
Вариант 1: клонировать сразу с подмодулями  
git clone --recurse-submodules https://github.com/user/main-project.git  
  
Вариант 2: если уже склонировали без флага  
git submodule init  
git submodule update  
Обновление подмодуля  
  
Перейти в папку подмодуля и сделать pull  
cd vendor/library  
git pull origin main  
cd ../..  
git add vendor/library  
git commit -m "Update library submodule"  
  
Или одной командой из корня (если настроен трекинг ветки)  
git submodule update --remote vendor/library  
Важно: submodule не следит за веткой автоматически. Он привязан к конкретному коммиту. Чтобы обновить — нужно явно указать это и закоммитить новый указатель в основном проекте.  
   
  
## Часть 2: Git Subtree  
  
Subtree вливает внешний репозиторий в поддиректорию основного проекта как обычные файлы и коммиты. Никакого .gitmodules, никаких дополнительных команд при клонировании — для пользователя это выглядит как обычная папка.  
  
Добавление  
git subtree add --prefix=<папка> <url> <ветка> --squash  
  
git subtree add --prefix=vendor/library https://github.com/user/library.git main --squash  
Флаг --squash сжимает всю историю внешнего проекта в один коммит. Без него в ваш репозиторий попадут все коммиты библиотеки, что раздует историю.  
  
Обновление (pull)  
  
git subtree pull --prefix=vendor/library https://github.com/user/library.git main --squash  
Работает как merge: изменения из upstream вливаются в указанную папку. Если были локальные правки в этой папке — они сохранятся, возможен конфликт, который разрешается обычным способом.  
  
Отправка изменений обратно (push)  
Если вы правили код библиотеки прямо в своём проекте и хотите отдать изменения в upstream:  
  
git subtree push --prefix=vendor/library https://github.com/user/library.git feature-branch  
Git «выделит» только коммиты, затрагивающие указанную папку, и запушит их как отдельную ветку в upstream.  
  
Извлечение папки в отдельный репозиторий (split)  
Обратная операция: вынести поддиректорию в самостоятельный репозиторий с сохранением истории.  
  
git subtree split --prefix=lib -b lib-branch  
Теперь ветку lib-branch можно запушить в новый репозиторий  
git push <new-repo-url> lib-branch:main  
Это создаёт «синтетическую» историю только по коммитам, затрагивающим lib/, с корнем в этой папке.  
  
  
## Часть 3: Когда что выбирать  
Submodule лучше, когда:  
  
Внешняя библиотека имеет свою команду разработки и независимый релизный цикл.  
Вы хотите точно зафиксировать версию зависимости (привязка к коммиту).  
Не планируете активно править код зависимости внутри своего проекта.  
  
Subtree лучше, когда:  
Вы хотите, чтобы проект клонировался одной командой без лишних телодвижений.  
Зависимость меняется редко, и вы готовы вливать её историю (или сжимать через --squash).  
Вы планируете активно править код зависимости как часть своего проекта и, возможно, отправлять изменения обратно.  
  
## Шпаргалка команд  
  
===== SUBMODULE =====  
git submodule add <url> <path>          # добавить  
git clone --recurse-submodules <url>    # клонировать с подмодулями  
git submodule update --init --recursive # инициализировать после клона  
git submodule update --remote <path>    # обновить до последнего коммита  
cd <path> && git pull && cd ..          # ручное обновление  
git add <path> && git commit            # зафиксировать новый указатель  
  
===== SUBTREE =====  
git subtree add --prefix=<path> <url> <branch> --squash   # добавить  
git subtree pull --prefix=<path> <url> <branch> --squash  # обновить  
git subtree push --prefix=<path> <url> <branch>           # отправить изменения  
git subtree split --prefix=<path> -b <branch>             # вынести в отдельную ветку  
  
  
  
  
# Git Tag  
Тег в Git — это статическая ссылка на конкретный коммит, которую обычно используют для маркировки релизов (v1.0, v2.0 и т.д.) . В отличие от ветки, тег не двигается вместе с новыми коммитами.    
   
Два типа тегов - Git поддерживает два вида тегов, и разница между ними принципиальна:  
  
**Аннотированный тег (-a)** хранится в базе Git как полноценный объект. Он содержит имя и email автора тега, дату, сообщение тега, и может быть подписан GPG. Это рекомендуемый тип для релизов .  
  
**Легковесный тег** — это просто указатель на коммит, как ветка, которая не меняется. Никакой дополнительной информации (автор, дата, сообщение) не сохраняется .  
  
Создание тегов:  
Аннотированный тег (на текущем коммите)  
  
**git tag -a v1.0 -m "Release version 1.0"**  
Флаг -m задаёт сообщение. Если его не указать, Git откроет редактор  
  
Легковесный тег  
  
**git tag v1.0-lw**  
Просто имя тега, без -a, -s или -m .  
  
Тег на конкретный коммит (задним числом)  
Если нужно пометить старый коммит, укажи его хеш в конце:  
**git tag -a v1.2 9fceb02 -m "Version 1.2"**  
  
Список всех тегов (в алфавитном порядке)  
git tag  
  
Поиск по шаблону  
**git tag -l "v1.*"**  
  
Информация о теге (для аннотированного — автор, дата, сообщение)  
**git show v1.0**  
Для легковесного тега git show покажет только информацию о коммите, без метаданных тега  
  
Отправка тегов на удалённый репозиторий  
Важно: git push по умолчанию не отправляет теги. Их нужно пушить явно.  
  
Один конкретный тег  
**git push origin v1.0**  
  
Все локальные теги, которых нет на remote  
**git push origin --tags**  
Нюанс: --tags отправляет и легковесные, и аннотированные. Если нужны только аннотированные — используй --follow-tags .  
  
Удаление тегов:  
Локально  
**git tag -d v1.0**  
  
На удалённом репозитории  
**git push origin --delete v1.0**  
Удаление локального тега не удаляет его на remote.  
  
Переключение на тег (detached HEAD)  
**git checkout v1.0**  
Ты попадёшь в состояние detached HEAD — это нормально для просмотра или сборки, но коммиты, сделанные в этом состоянии, не будут привязаны ни к одной ветке .  
  
Если хочешь начать работу от тега:  
**git switch -c hotfix-v1.0**  
Так создаётся новая ветка от коммита, на который указывает тег.  
  
Пересоздание тега (опасно!)  
Если ты пометил не тот коммит и тег ещё не был запушен:  
**git tag -f v1.0 <правильный-коммит>**  
Если тег уже был запушен, делать -f и force-push опасно: у других людей может остаться старая версия тега с тем же именем. Официальная рекомендация — просто выпустить новый тег с другим именем (например, v1.0.1) .  
  
Шпаргалка  
  
Создание  
git tag -a v1.0 -m "message"____________аннотированный  
git tag v1.0____________________________легковесный  
git tag -a v1.0 <hash> -m "msg"_________на конкретный коммит  
  
Просмотр  
git tag________________список  
git tag -l "v1.*"______поиск  
git show v1.0__________детали  
  
Публикация  
git push origin v1.0______________один тег  
git push origin --tags____________все теги  
git push origin --follow-tags_____только аннотированные  
  
Удаление  
git tag -d v1.0______________________локально  
git push origin --delete v1.0________на remote
